# [P3] CIBA 認証デバイス UI のログイントランザクション生成に上限を設ける

## ステータス

🟢 Low / 未着手

## 背景

生成 OP の `GET /ciba`（認証デバイス UI）は、OP セッションを持たないアクセスのたびに 600 秒 TTL の `CibaLoginTransactionRecord` を無条件に発行し、ストアへ保存する。
この経路は CIBA 機能が足す面のうち唯一「未認証・無条件で書き込みが発生する」もので、in-memory ストアの掃除は保存時に期限切れレコードを消すだけのため、TTL 窓内では到達者がレコード数を際限なく増やせる（1 レコードあたり 256 ビット乱数 2 本と SHA-256 ハッシュ分のメモリ）。

対比として、device flow のバインディングは有効な `user_code` の一致後にしか発行されず、`POST /backchannel_authentication` はクライアント認証と subject 単位の上限で守られている。
in-memory ストアは開発用と明記されているが、CLI が既定で生成し既定で動く構成でもあるため、他ストアと同様の天井（総数上限）を設けるか、デプロイ層の流量制御に委ねる判断を明文化するかを決めたい。
2026-09-30 の実装レビュー（Phase 2 ルーティーン）で検出した。

## 対象ファイル

- `packages/experimental/src/ciba/store.ts`（in-memory ログイントランザクションストアの上限、または契約コメントでの責務明記）
- `packages/cli/src/frameworks/hono/templates.ts`（`GET /ciba` のトランザクション発行部。上限超過時の応答）
- CIBA の単体テスト・生成 conformance テスト
- 実装解説 `implementation-guides/experimental/ciba.{ja,en}.md`（掲載コードの同期）

## 仕様参照

- CIBA Core 1.0（認証デバイス UI 自体は仕様外の実装領域。DoS 考慮は一般原則）
- RFC 9700 §2.5（アプリ層のリソース枯渇への考慮）
- 先例: `p2-login-attempt-throttling-subject-scope.md`（ログイン試行の抑制）、PAR / Device の各ストアの TTL 設計

## 検討の観点

- 総数上限を入れる場合、上限到達時の応答（新規トランザクションを発行せず画面を返すか、エラーにするか）がセッション有無のオラクルにならない形を選ぶ
- IP 単位の流量制御はデプロイ層の責務とする既存方針（device の user_code 推測面と同じ整理）との線引きを明記する

## 修正方針

- [ ] in-memory ストアに総数上限（他ストアの既定に倣った値）を入れるか、責務外と明文化するかを決める
- [ ] 上限を入れる場合は超過時の挙動を fail-closed かつ非オラクルに設計する
- [ ] 判断を実装コメントと実装解説へ記録する

## 完了条件

- 上限の有無どちらに決めても、判断・根拠・挙動がコード・テスト・実装解説で一致している
