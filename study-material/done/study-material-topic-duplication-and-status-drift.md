# `study-material/` のトピック重複とステータス陳腐化（調査資産のメンテナンス性）

## ステータス

🟡 Medium（調査資産の品質）/ 未着手

## 1. このトピックで確認したいこと

`study-material/` は本ファイル作成時点で 113 ファイル、`study-material/done/` は 83 ファイル、`tasks/`（`done/` 含む）は
約 150 ファイルという規模に達している。この規模になると、調査資産そのものの品質——
**同じトピックが複数ファイルに分裂していないか**、**ステータスが実装の現状と一致しているか**——が、
新しい調査の精度に直接影響する。

本ファイルで確認したいのは次の 2 点である。

1. **重複トピック**: 同一の仕様・同一の改善案を扱うファイルが複数存在していないか
2. **ステータス陳腐化**: すでに実装済みの機能が「未着手」と書かれたまま残っていないか

これは仕様準拠そのものの論点ではなく、**リポジトリの調査プロセスが自己矛盾を起こしていないか**の論点である。
CLAUDE.md および継続調査タスクの指示は「新しいトピックファイルを作る前に
`study-material/` / `study-material/done/` / `tasks/` をすべて確認し、同じ論点が既に扱われていないか
確認すること」を明示的に求めている。重複ファイルが存在する状態は、**この確認手順そのものを機能不全にする**。

## 2. 関連する仕様・基準

本トピックは外部仕様への準拠ではなく、リポジトリ内部の運用規約への準拠を扱う。根拠は次のとおり。

- **CLAUDE.md「レビュー内容について」および継続調査タスクの「重複記載を避ける方針」**:
  - 「すでに `study-material/` / `study-material/done/` / `tasks/` のいずれかで扱っている内容については、
    同じ説明を繰り返さないでください」
  - 「新しいトピックのファイルを作成する前に、上記すべてのディレクトリを確認し、
    同じ論点・同じ仕様・同じ改善案がすでに扱われていないかを確認してください」
  - 「既存ファイルの内容を更新した方が自然な場合は、新規ファイルを作成せず、既存ファイルに追記・修正する」
- **CLAUDE.md「リリース方針」**: 「動くものを早く出して改善する」を優先する一方で、
  「テストコードで主要ケースを網羅し、仕様参照を明記することは必須」。
  調査資産は仕様参照の一次的な集約点であり、その正確性はリリース方針の前提になっている。

外部仕様の説明は本ファイルでは行わない（重複回避）。各重複ペアが扱う仕様の内容は、
統合先として選ばれたファイル側に残す。

## 4. 現在の実装確認

### 4.1 確認された重複トピックペア（5 組）

いずれも `study-material/` 直下に、**同一トピックを扱う 2 ファイル**が並存している。

| # | ファイル A | 行数 | ファイル B | 行数 | 扱うトピック |
|---|---|---|---|---|---|
| 1 | `audit-logging-and-observability.md` | 134 | `audit-logging-observability.md` | 137 | 監査ログ / 可観測性 |
| 2 | `ext-native-apps-rfc8252.md` | 129 | `ext-oauth-native-apps-rfc8252.md` | 100 | RFC 8252 Native Apps |
| 3 | `ext-dynamic-client-registration.md` | 94 | `extension-dynamic-client-registration.md` | 75 | OIDC DCR 1.0 / RFC 7591 |
| 4 | `ext-pushed-authorization-requests-rfc9126.md` | 95 | `extension-pushed-authorization-requests-par.md` | 75 | PAR / RFC 9126 |
| 5 | `amr-values-guidance-rfc8176.md` | 169 | `amr-values-rfc8176.md` | 124 | RFC 8176 `amr` 値 |

命名パターンから、`ext-*`（新しい命名規約）と `extension-*` / 接尾辞なし（旧命名）が
別々の調査回で作られ、統合されないまま残ったものと推測される。
（**推測**であり、コミット履歴での裏取りは未実施。統合作業時に `git log --follow` で確認するとよい。）

### 4.2 `done/` との三重複（1 組）

- `study-material/done/oauth-native-apps-rfc8252.md` — **タスク化済み**として `done/` に移動されている
- `study-material/ext-native-apps-rfc8252.md` — 未処理として直下に残存
- `study-material/ext-oauth-native-apps-rfc8252.md` — 同上

すなわち RFC 8252 のトピックは **1 つが done、2 つが pending** という状態にある。
`done/` へ移動済みのトピックが直下にも残っているため、
「done を確認してから新規作成する」という手順を踏んでも重複を検出できない。

### 4.3 ステータス陳腐化（PAR）

PAR（RFC 9126）は**すでに実装されている**:

- `packages/experimental/src/par/` — `par-request.ts` / `resolve-request-uri.ts` / `store.ts` および対応するテスト
- `packages/cli/src/features.ts` — `EXPERIMENTAL_FEATURES = ['par']`、`ProviderFeatures.par: boolean`（既定 `false`）
- `tests/e2e/specs/pushed-authorization-requests.spec.ts` — E2E テスト

にもかかわらず、`study-material/ext-pushed-authorization-requests-rfc9126.md` のステータス欄は
**「🟢 拡張機能 / 未着手」**のままである（もう一方の `extension-*` 側も同様に導入検討の体裁）。

この状態は、次回以降の調査で「PAR は未実装だから提案しよう」という**誤った結論**を導きうる。
実装済み機能に対する調査ファイルは、`done/` へ移すか、
「実装済み。残課題は X」という差分ファイルへ書き換えるのが妥当である。

### 4.4 影響を受けない部分（確認済み）

- `study-material/done/` 内での重複は確認されなかった。
- `tasks/` / `tasks/done/` 内での重複は確認されなかった。
- 命名規約自体は `ext-*` に概ね収束しており、規約の不在ではなく**移行の取り残し**が原因と見られる。

## 5. 現在の実装との差分

### 5.1 満たしていること

- 重複回避の方針は CLAUDE.md および継続調査タスクに明文化されている。
- インデックスファイル（`basic-op-requirements-baseline.md` / `basic-op-requirement-traceability.md`）が
  存在し、「重複記載しない」ことを自ら宣言している。
- `study-material/` → `study-material/done/` → `tasks/` というライフサイクルが定義されている。

### 5.2 不足している可能性があること

- 🟡 **重複の検出手段が無い**: 重複回避が「調査者が毎回 3 ディレクトリを目視確認する」ことに依存しており、
  ファイル数が 200 を超えた現在、人間にも AI にも現実的でない。
- 🟡 **命名規約が文書化されていない**: `ext-` 接頭辞が拡張機能トピックを表す規約であることは
  ファイル名から読み取れるが、CLAUDE.md には記載が無い。`extension-*` が混在した原因はここにある可能性が高い。
- 🟡 **ステータス更新のトリガーが無い**: 機能が実装されても、対応する study-material のステータスを
  更新する手順が定義されていない（PAR がその実例）。
- 🟡 **`done/` への移動条件が「タスク化した時」のみ**: 「タスク化せずに実装された」「調査の結果不要と判断した」
  ケースの行き先が定義されていない。

### 5.3 セキュリティ上の観点

直接のセキュリティ影響は無い。ただし間接的な影響として、
**重複ファイル間で結論が食い違った場合、どちらが最新の判断か分からなくなる**リスクがある。
セキュリティ方針（例: `amr` 値の扱い、Native Apps の redirect_uri ポリシー）が
2 ファイルに分裂していると、実装時に古い方を参照する事故が起こりうる。
統合時には**結論の差分**を必ず確認すべきである。

### 5.4 相互運用性の観点

該当なし（リポジトリ内部の資産管理の論点）。

### 5.5 Basic OP として確認すべきこと

Basic OP 認定には**影響しない**。ただし `basic-op-requirement-traceability.md` が
「Basic OP 要件 → 実装 → テスト → 既存タスク」のトレーサビリティ・マトリクスとして機能するには、
参照先ファイルが一意である必要がある。重複はこのマトリクスの信頼性を下げる。

## 6. 改善・追加を検討する理由

- **なぜ価値があるか**: 本リポジトリの差別化軸のひとつは **Speed（新仕様への最速追随）**である。
  新しい仕様が出たときに「既に調べたか / どこまで調べたか」を即座に判断できることが Speed の前提になる。
  重複と陳腐化はこの判断を毎回やり直させるコストとして効いてくる。
- **Basic OP 必須か拡張か**: どちらでもない。**調査プロセスの保守**。
- **導入しやすさ**: 統合作業自体は機械的で、コード変更を一切伴わない。リスクが低い。
  一方で「どちらのファイルを残すか」「結論が食い違う箇所をどう解決するか」には人間の判断が要る。
- **既存実装との接続**: コードには接続しない。`basic-op-requirement-traceability.md` の参照リンクと、
  CLAUDE.md の命名規約セクション（新設する場合）に接続する。
- **利用者・開発者のメリット**: 本リポジトリの `study-material/` は OSS として公開されており、
  「OIDC の実装検討でどこを見るべきか」という資産としても読まれうる。重複の無い状態はその価値を高める。
- **実装しない場合のリスク**: ファイル数は今後も増える。重複ペアが 5 組ある状態を放置すると、
  次の調査回で 6 組目・7 組目が生まれる。統合コストは単調増加する。

## 7. 実装方針の候補

> 最終判断は人間が行う。以下は判断材料の整理。

### 方針A: 5 組を手作業で統合し、命名規約を CLAUDE.md に明記する

各ペアについて、内容が厚い方（または新しい命名規約 `ext-*` に沿う方）を残し、
もう一方の固有情報を移植してから削除する。あわせて CLAUDE.md に
「拡張機能トピックは `ext-<仕様略称>.md`」という規約を追記する。

- 利点: 根本解決。今回の 5 組は確実に消える。
- 欠点: 統合時に**結論の食い違い**を人間が解決する必要がある（特に `amr-*` の 2 ファイルは
  169 行 / 124 行と両方が厚く、単純な包含関係ではない可能性が高い）。
- 留意: 削除ではなく**統合**であること。片方を消すだけだと固有の論点が失われる。

### 方針B: 統合はせず、重複ペアに相互参照ヘッダを入れる

各ファイルの冒頭に「本トピックは `<相手ファイル>` とも重複する。統合予定」と明記する。

- 利点: 最小コスト。結論の食い違いを解決しなくてよい。
- 欠点: ファイル数は減らず、確認コストも下がらない。**先送りにしかならない**。

### 方針C: 重複検出を CI で機械化する

`study-material/` のファイル名と見出しから正規化キー（例: RFC 番号・仕様名）を抽出し、
衝突があれば CI で警告する軽量スクリプトを追加する。

- 利点: 6 組目以降の発生を防げる。継続調査が AI によって自動実行される運用と相性が良い。
- 欠点: 誤検知の調整が要る。既存 5 組を先に解消しないと常時赤になる（方針 A との併用が前提）。
- 実装イメージ: `scripts/` 配下に Node スクリプトを置き、ファイル名から
  `rfc\d+` / `oidc-\w+` 等のトークンを抽出して重複を検出する。外部依存は不要。

### 方針D: ステータス陳腐化の解消手順を定義する

「機能を実装したら、対応する `study-material/` ファイルを `done/` へ移すか、
残課題のみの差分ファイルへ書き換える」という手順を CLAUDE.md に追記する。
PAR の 2 ファイルはこの手順の最初の適用対象になる。

- 利点: 陳腐化の再発を防ぐ。PAR という具体例があるため手順を書きやすい。
- 欠点: 手順を書いても実行されなければ意味がない（方針 C の機械化と併用すると実効性が上がる）。

### 組み合わせの目安

- 今回の負債を確実に返す: **A + D**
- 再発防止まで含める: **A + C + D**
- B は単独では効果が薄く、A へ進む前の暫定措置としてのみ意味がある
