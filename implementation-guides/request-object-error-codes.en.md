# Returning `invalid_request_object` for Request Object Validation Failures

This guide covers the authorization request validation in `@maronn-openid-connect/core` and the contract tests generated by the CLI.
The work was implemented from the task `tasks/done/p2-authorization-error-invalid-request-object.md` in the OSS repository.

## What the feature does

An OpenID Provider can receive a **Request Object** (a JWT whose claims are the authorization request parameters, OIDC Core 1.0 §6.1) through the `request` parameter of an authorization request.
This library already implements Request Object by value, but until now every parse or signature-verification failure was reported with the generic error code `invalid_request`.
With this change, validation failures are reported with the dedicated code `invalid_request_object` defined in OIDC Core 1.0 §6.3.

§6.3 defines four error codes related to Request Objects:

- **`invalid_request_uri`**: the `request_uri` is unreachable, or returns an error or invalid data
- **`invalid_request_object`**: the `request` parameter contains an invalid Request Object
- **`request_not_supported`**: the OP does not support the `request` parameter at all
- **`request_uri_not_supported`**: the OP does not support the `request_uri` parameter

Before this change, the `AuthorizationErrorCode` enum contained only the latter two.
The enum's comment explicitly cited §6.3, so the absence of the first two was judged to be an implementation gap rather than a design decision.
During implementation, the definitions of all four codes were verified against the Authentication Error Response error-code table in OIDC Core 1.0 (`invalid_request_object`: "The request parameter contains an invalid Request Object.").

## Use cases

Distinguishing these error codes changes what a client developer does next.
A client receiving `request_not_supported` should stop using Request Objects, while a client receiving `invalid_request_object` should fix its own Request Object construction (signing key, `alg`, JWS assembly).
The two remedies point in opposite directions, yet before this change both situations could produce the same failure report (the latter as `invalid_request`), so troubleshooting could not start from the error response.

A second motivation is integration with the extension packages.
The experimental PAR implementation (RFC 9126) needs `invalid_request_uri`, but because the core enum lacked it, PAR defined its own error class `PushedRequestUriError` as a workaround.
Now that `invalid_request_uri` is part of the enum, that workaround can eventually be folded into core's error type (the folding itself remains a separate task).
Both codes will also be required if JAR (RFC 9101) is formally supported in the future.

## Design decisions

The change is limited to adding two enum values and swapping the conversion target at a single site.

First, no existing enum member or serialized value changed.
Adding enum values is backward compatible, and the other validations that report `invalid_request` (missing required parameters and so on) are untouched.

Second, the non-redirect behavior is preserved.
Request Object parsing runs before redirect_uri resolution, so a validation failure produces an `AuthorizationError` without `redirectUri` / `state`, rendered as an error page on the OP rather than a redirect to the client.
A redirect_uri carried inside a broken Request Object cannot be trusted, so this design has to stay.
This change swaps only the error code, and the tests now pin that the behavior did not change.

Third, `invalid_request_object` is produced at exactly one place: the site that converts `RequestObjectError`.
Every failure thrown by `parseRequestObject` (broken JWS structure, JWE input, missing or unsupported `alg`, `alg: "none"` received while disallowed, no client JWKS registered, no key matching `kid`, signature verification failure) flows through that single site, so one swap makes all cases conform to §6.3.
The `request_not_supported` response for configurations that disable the Request Object feature is produced by a different function and is unchanged.

For semver, core is a minor bump and cli a patch.
Core gains new enum values, and the error code visible to clients changes; the changeset notes that clients which assumed `invalid_request` may be affected.
The cli change only alters the contract tests the templates emit, hence patch.

## Changed code in core

### packages/core/src/authorization-request.ts: the error-code enum

The two §6.3 values were added to `AuthorizationErrorCode`.
The full enum after the change:

```typescript
/**
 * 認可エンドポイントのエラーコード
 * OAuth 2.1 Section 4.1.2.1 / OIDC Core 1.0 Section 3.1.2.6
 */
export enum AuthorizationErrorCode {
  // OAuth 2.1 Section 4.1.2.1
  InvalidRequest = 'invalid_request',
  UnauthorizedClient = 'unauthorized_client',
  AccessDenied = 'access_denied',
  UnsupportedResponseType = 'unsupported_response_type',
  InvalidScope = 'invalid_scope',
  ServerError = 'server_error',
  TemporarilyUnavailable = 'temporarily_unavailable',
  // OIDC Core 1.0 Section 3.1.2.6
  InteractionRequired = 'interaction_required',
  LoginRequired = 'login_required',
  AccountSelectionRequired = 'account_selection_required',
  ConsentRequired = 'consent_required',
  // OIDC Core 1.0 Section 6.3: returned when the request_uri is unreachable or
  // yields invalid data, or the request parameter carries an invalid Request Object.
  InvalidRequestUri = 'invalid_request_uri',
  InvalidRequestObject = 'invalid_request_object',
  // OIDC Core 1.0 Section 6.3: returned when the OP does not support the
  // request / request_uri parameters but the client used them.
  RequestNotSupported = 'request_not_supported',
  RequestUriNotSupported = 'request_uri_not_supported',
  // OIDC Core 1.0 §3.1.2.6: returned when the OP does not support the `registration`
  // parameter (Self-Issued OP RP metadata, §7.2.1) but the client used it.
  RegistrationNotSupported = 'registration_not_supported',
}
```

`InvalidRequestUri` is not used by any conversion path in this change.
It was added at the same time so the enum carries all four §6.3 codes, removing the constraint that forced experimental PAR to invent its own error type.

### packages/core/src/authorization-request.ts: the conversion site

The step function `resolveRequestObjectParams` resolves the Request Object and converts the `RequestObjectError` thrown by `parseRequestObject` into an `AuthorizationError`.
The conversion target changed from `InvalidRequest` to `InvalidRequestObject`.
The full function after the change:

```typescript
/**
 * Request Object by value（OIDC Core 1.0 §6.1）を解決する（機能単位のステップ関数）。
 *
 * `request` パラメータが無い場合はクエリパラメータのコピーをそのまま返す。
 * ある場合は署名付き JWS Request Object をクライアント登録鍵（`ClientInfo.jwks`）で
 * 検証し、claim をクエリ値に supersede した有効パラメータ集合を返す。検証失敗
 * （壊れた JWT / 未対応 alg / 鍵不一致 / 署名不一致）は信頼できないため、
 * 内部の redirect_uri も信用せず非リダイレクトの invalid_request_object
 * （OIDC Core 1.0 §6.3）とする。
 *
 * `response_type` / `client_id` は OAuth 2.0 request syntax 側を正とするため
 * 上書きしない（後段の {@link validateRequestObjectConsistency} で一致検証する）。
 */
export async function resolveRequestObjectParams(
  params: AuthorizationRequestParams,
  client: ClientInfo,
  options: {
    /**
     * 受理する JWS 署名アルゴリズム。
     * 未指定なら {@link DEFAULT_REQUEST_OBJECT_SIGNING_ALGS}（`["RS256"]`）。
     */
    supportedSigningAlgs?: string[];
    /**
     * 署名無し（`alg: "none"`）Request Object を互換受理するか。既定 false（署名必須）。
     * OIDF Conformance Suite 互換の場合のみ true にする。
     */
    allowUnsigned?: boolean;
  } = {},
): Promise<ResolvedRequestObjectParams> {
  if (params.request === undefined) {
    return { effectiveParams: { ...params } };
  }

  let requestObjectClaims: Record<string, unknown>;
  try {
    requestObjectClaims = await parseRequestObject(params.request, {
      jwks: client.jwks,
      supportedSigningAlgs:
        options.supportedSigningAlgs ?? [
          ...DEFAULT_REQUEST_OBJECT_SIGNING_ALGS,
        ],
      allowUnsigned: options.allowUnsigned ?? false,
    });
  } catch (e) {
    if (e instanceof RequestObjectError) {
      // OIDC Core 1.0 §6.3: an invalid Request Object is reported as
      // invalid_request_object, distinguishing "fix your Request Object"
      // from request_not_supported ("stop using the request parameter").
      throw new AuthorizationError(
        AuthorizationErrorCode.InvalidRequestObject,
        e.message,
      );
    }
    throw e;
  }

  return {
    effectiveParams: mergeRequestObjectParams(params, requestObjectClaims),
    requestObjectClaims,
  };
}
```

### packages/core/src/request-object.ts: the error class doc comment

The behavior of `RequestObjectError` itself is unchanged.
Only its doc comment, which states what code the caller converts it to, was updated to match the new conversion target.

```typescript
/**
 * Request Object のパース・署名検証に失敗したことを表すエラー。
 *
 * 呼び出し側（`validateAuthorizationRequest`）はこれを捕捉して
 * `invalid_request_object`（OIDC Core 1.0 §6.3）の `AuthorizationError` に変換する。
 */
export class RequestObjectError extends Error {
  constructor(message: string) {
    super(message);
    this.name = 'RequestObjectError';
  }
}
```

## Tests in core

The work followed TDD: the tests expecting `InvalidRequestObject` were made Red first, then the implementation turned them Green.
The conditions under which `parseRequestObject` throws `RequestObjectError` did not change, so the existing 11 cases in `request-object.test.ts` (broken structure, JWE, `alg: "none"` handling, missing JWKS, unknown `kid`, signature mismatch, and so on) pass unmodified.

## Contribution to the CLI-generated code

Because the observable behavior of the generated OP (the error code) changes, the generated contract tests in `conformance.test.ts` were updated within the same change, as the repository conventions require.
The template is `requestObjectValueConformanceBlock` in `packages/cli/src/frameworks/hono/templates.ts`, shared by both the hono and web-standard (express / fastify / nextjs) templates.
A single addition therefore lands in the generated output of all four frameworks.

### The test added to the generated conformance.test.ts

The following test is added to the "Request Object by value (OIDC Core 1.0 §6.1)" describe.
It pins, by exact match against the default error page HTML, that the OP shows an `invalid_request_object` error page for a broken Request Object instead of redirecting.

```typescript
    it('should reject a broken request object with a non-redirect invalid_request_object error page', async () => {
      const url =
        '/authorize?response_type=code&client_id=c-conf' +
        '&redirect_uri=' + encodeURIComponent(REDIRECT_URI) +
        '&scope=openid&state=req-broken' +
        '&request=not-a-jwt' +
        '&code_challenge=' + PKCE_CHALLENGE_S256 + '&code_challenge_method=S256';
      const res = await app.request(url);

      // OIDC Core 1.0 §6.3: the request parameter contains an invalid Request
      // Object, so the OP reports invalid_request_object (not the generic
      // invalid_request). A redirect_uri carried inside a broken Request Object
      // cannot be trusted, so the error stays on the OP: HTTP 400, no redirect,
      // no state echo. Pinned to the default error page so a change in either
      // the error code or the non-redirect behavior is caught exactly.
      expect(res.status).toBe(400);
      expect(res.headers.get('Location')).toBe(null);
      expect(res.headers.get('Content-Type')).toBe('text/html; charset=UTF-8');
      const body = await res.text();
      expect(body).toBe(
        [
          '<!DOCTYPE html>',
          '<html>',
          '<head><title>Error</title></head>',
          '<body>',
          '  <h1>Error</h1>',
          '  <p>invalid_request_object</p>',
          '  <p>request object is not a JWS compact serialization</p>',
          '</body>',
          '</html>',
        ].join('\n'),
      );
    });
```

All four samples (hono-cloudflare / express-flyio / fastify-flyio / nextjs-vercel) were regenerated with the CLI, and the diff of the generated output consists only of this added test.
The generated OP's route implementation itself is unchanged.
The authorize route uses the `error` property of `AuthorizationError` directly for both rendering and redirecting, so swapping the conversion target in core is enough to change the generated OP's responses.
